# 01 原项目架构分析（基于本地 v0.17.0 代码实测）

> 依据：`D:\gpt-researcher`，分支 `feature/adaptive-reliable-research`（从本地 `main` 切出，代码未做任何修改）
> 方法：逐文件阅读 + 交叉验证调用关系，不使用 README / DeepWiki 的推断结论
> 规模：核心包 `gpt_researcher/` 共 **129 个 `.py` 文件**；`tests/` 共 **181 个测试文件**

---

## 1. 项目定位与技术栈

GPT Researcher 是一个"给定研究问题 → 自动搜索 → 抓取网页 → 压缩上下文 → 生成带引用报告"的自主研究 Agent。v0.17.0 已从早期单脚本演进为四层结构：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 核心库 | `gpt_researcher/` | 研究流程本体（LLM、检索、抓取、上下文、报告），可被任意宿主调用 |
| Web 应用层 | `backend/` + `frontend/` | FastAPI + WebSocket 实时日志 + Next.js 前端，负责交互与报告文件落盘 |
| 多 Agent 应用 | `multi_agents/` | 基于 **LangGraph** 的"总编—研究员—写手—核查—发布"工作流 |
| 实验/评测 | `deep_agents/`、`evals/` | 另一套基于 `deepagents` 包的实验实现；三套离线评测框架 |

技术栈关键事实：

- **不是** LangGraph 单一架构。LangGraph 只用于 `multi_agents/`；标准研究流程是**纯 async 函数流水线**（`asyncio.gather` 并发），这是本项目最重要的架构事实。
- LLM 访问统一走 `langchain` 生态（`llm_provider/generic/base.py` 封装各家 provider）。
- 上下文压缩用 `langchain_classic` 的 `ContextualCompressionRetriever` + `EmbeddingsFilter`。
- 状态**没有**统一 State 对象（标准模式），而是挂在 `GPTResearcher` 实例属性上（见第 6 节）。

## 3. 核心包 `gpt_researcher/` 模块详解

### 3.1 `agent.py`：唯一对外入口类 `GPTResearcher`

- 对外只暴露一个类：`gpt_researcher/__init__.py` → `from .agent import GPTResearcher`。
- 构造函数 `GPTResearcher.__init__`（`agent.py:55-207`）做了三件事：
  1. 解析配置：`self.cfg = Config(config_path)`；
  2. 组装 6 个协作对象（组合而非继承）：
     - `self.research_conductor = ResearchConductor(self)`（`skills/researcher.py`）
     - `self.report_generator = ReportGenerator(self)`（`skills/writer.py`）
     - `self.context_manager = ContextManager(self)`（`skills/context_manager.py`）
     - `self.scraper_manager = BrowserManager(self)`（`skills/browser.py`）
     - `self.source_curator = SourceCurator(self)`（`skills/curator.py`）
     - `self.deep_researcher = DeepResearchSkill(self)`，**仅当** `report_type == "deep"`（`agent.py:198-199`）
  3. 维护实例状态：`context`、`visited_urls`、`research_sources`、`research_costs`、`step_costs`、`_current_step`。
- 关键方法：
  - `conduct_research()`（`agent.py:353`）：编排"选 Agent → 研究 → 可选图片生成"；
  - `write_report()`（`agent.py:473`）：调用 `ReportGenerator.write_report`；
  - `get_subtopics()/get_draft_section_titles()`：供 `DetailedReport` 使用；
  - `quick_search()`（`agent.py:541`）：不跑完整流程的快速检索 + 摘要（`deep_agents` 的工具就是它）；
  - `add_costs()`（`agent.py:795`）：成本记账回调，按 `_current_step` 分桶到 `step_costs`。
- **设计要点**：所有子模块都持有 `researcher` 反向引用（`self.researcher.xxx`），形成"中心对象 + 卫星技能"的星形耦合。这既是扩展点（新模块可拿到完整上下文），也是改造成本来源（任何状态字段都长在中心对象上）。

### 3.2 `skills/`：有状态的流程技能

| 文件 | 类 | 实际职责 |
| --- | --- | --- |
| `skills/researcher.py`（1148 行） | `ResearchConductor` | **研究主流程**：计划子查询 → 并发搜索 → 抓取 → 压缩 → 合并 context；MCP 检索器策略（fast/deep/disabled）也在这里 |
| `skills/deep_research.py`（670 行） | `DeepResearchSkill` | **递归式深度研究**：breadth×depth，每轮生成 learnings + followUpQuestions，递归下钻，最后按 25000 词裁剪 |
| `skills/writer.py`（236 行） | `ReportGenerator` | 报告正文 / 引言 / 结论 / 子主题 / 草稿标题 |
| `skills/curator.py`（114 行） | `SourceCurator` | 一次 LLM 调用给来源打可信度/相关性评分并筛选（`CURATE_SOURCES=True` 时启用，默认关闭） |
| `skills/context_manager.py`（163 行） | `ContextManager` | 上下文选择与压缩入口，失败时降级为关键词排序（`context/lexical.py`） |
| `skills/browser.py` | `BrowserManager` | 并发抓取 URL（`browse_urls`），内部调用 `scraper/` |
| `skills/image_generator.py` | `ImageGenerator` | 可选配图 |

### 3.3 `actions/`：无状态函数层

`actions/` 是"可被任意调用的纯函数集合"，不持有状态，全部通过参数拿配置与回调：

- `agent_creator.choose_agent()`（`agent_creator.py:18`）：一次 LLM 调用产出 `(agent_role, role_prompt)`，带 JSON 修复兜底（`handle_json_error`、`extract_json_with_regex`）。
- `query_processing.get_search_results()` / `generate_sub_queries()` / `plan_research_outline()`：**规划只做一件事——生成 N 条子查询**。
- `retriever.get_retriever()/get_retrievers()`：把配置里的检索器名解析成类，支持 **entry_points 插件**（`RETRIEVER_ENTRY_POINT_GROUP`）。
- `web_scraping.scrape_urls()`：抓取 + 清洗 + 过滤（`filter_urls`）。
- `report_generation.generate_report()`：拼 prompt → 调用 LLM 出报告（`report_generation.py:209`）。
- `markdown_processing`：`extract_headers`、`extract_sections`、`table_of_contents`、`add_references`（**引用章节由 `visited_urls` 生成**）。

### 3.4 `context/`：上下文压缩与选择

- `compression.py`：`ContextCompressor.async_get_context()`（`compression.py:148`）—— 文档切块（1000/100）→ `EmbeddingsFilter` 相似度过滤（阈值默认 0.42/环境变量 `SIMILARITY_THRESHOLD`）→ 格式化；**小文档走快路径**（总字符 < `COMPRESSION_THRESHOLD` 默认 8000 且条数 ≤ max_results 时直接返回，省 embedding 费用）。
- `select.py`：`select_context()` 统一入口，按 `CONTEXT_FILTER` 选择压缩后端（`compression` / `jev_filter` / `lexical` / `noop`）。
- `lexical.py`：无 embedding 时的关键词排序降级路径。

### 3.5 `retrievers/` / `scraper/`

- `retrievers/`：24 个目录形态的检索器（tavily、bing、brave、duckduckgo、arxiv、pubmed、semantic_scholar、exa、mcp…），**按目录自动发现**（`retrievers/utils.py get_all_retriever_names()`），并支持第三方插件。
- `scraper/scraper.py:116 class Scraper`：统一抓取器，按 `SCRAPER` 配置选择 `beautiful_soup / browser(nodriver) / firecrawl / tavily_extract / pymupdf / arxiv / web_base_loader`。
- 抓取是整条链路里**最慢最不稳定**的一环，已有并发控制（`MAX_SCRAPER_WORKERS`）与限速（`SCRAPER_RATE_LIMIT_DELAY`）。

### 3.6 `llm_provider/`：统一 LLM 抽象

- `GenericLLMProvider.from_provider(provider, **kwargs)`（`utils/llm.py:27 get_llm`）。
- 三档模型：`fast_llm` / `smart_llm` / `strategic_llm`（各自 `provider:model` 字符串），由 `Config.parse_llm()` 拆分。
- `utils/llm.py:41 create_chat_completion()` 是**全项目唯一的 LLM 调用收口**：
  - 统一重试（非流式最多 10 次，指数退避）；
  - 每次调用后用 `calculate_llm_cost()` 计算美元成本并回调 `cost_callback`；
  - 支持 `reasoning_effort`、`llm_kwargs` 覆盖。

> 这一点对改造极其关键：**只要在 `create_chat_completion` 这一层加计数/预算钩子，就能覆盖全项目所有 LLM 调用**。

### 3.7 `prompts.py`：Prompt 家族

- `class PromptFamily`（`prompts.py:14`）+ 子类 `GranitePromptFamily` / `Granite3/3.1/3.2`。
- 通过 `get_prompt_family(name, cfg)`（`prompts.py:889`）选择，实例挂在 `researcher.prompt_family`。
- 关键方法：`generate_search_queries_prompt`（`prompts.py:213`）、`curate_sources`（`:319`）、`generate_report_prompt`（`:262`）、`generate_subtopics_prompt`（`:573`）。
- **注意**：`generate_search_queries_prompt(max_iterations=cfg.max_iterations)`（`prompts.py:217,246-248`）里的 "max_iterations" **只是"生成几条查询"的数量**，不是循环次数。这是本项目里最容易误读的命名（详见 04 号文档）。

### 3.8 `config/`、`utils/`、`observability.py`、`mcp/`、`memory/`、`vector_store/`、`document/`

- `config/config.py`：`Config` 把 `variables/default.py` 默认值与 `os.getenv` 合并，提供 `parse_retrievers/parse_llm/parse_embedding/parse_reasoning_effort`；配置项约 50 个（`variables/base.py` 有完整类型声明）。
- `utils/llm.py`：LLM 收口；`utils/costs.py`：**按 token 估算美元**（`tiktoken` + 内置价目表，`calculate_llm_cost` 优先用 provider 返回的 usage_metadata，缺失时用 tiktoken 估算）；`utils/logger.py`、`logging_config.py`（JSON 日志 handler）、`validators.py`（pydantic `Subtopics`）、`url_security.py`（URL 白名单/黑名单）。
- `observability.py`：`ResearchObserver` 协议 + `emit_research_event()`——**失败隔离的生命周期事件钩子**（`agent.py`、`skills/researcher.py` 里大量 `_emit_research_event`：`search_failed`、`candidate_discovered`、`selected_for_fetch`、`content_prefetched`…）。这是"过程可观测"的现成基础设施。
- `mcp/`：MCP 协议客户端与工具选择（两阶段：LLM 选工具 → 调用）。
- `memory/`、`vector_store/`、`document/`：embedding、向量库、本地/在线文档加载。

## 4. 应用层：`backend/`

- `backend/server/app.py`：FastAPI 应用（`/report/`、`/api/reports`、`/ws`、`/upload/`、`/api/chat`、`/api/multi_agents` 等）。
- `backend/server/server_utils.py`：`CustomLogsHandler`（把过程日志写 `outputs/*.json` 并推送 WebSocket）、`handle_start_command()`、`generate_report_files()`（md/pdf/docx）。
- `backend/report_type/`：三种报告模式适配器：
  - `BasicReport`（`basic_report.py:72 run()`）：`conduct_research()` → `write_report()`；
  - `DetailedReport`（`detailed_report.py:10`）：先研究 → 生成子主题 → **每个子主题一个独立 `GPTResearcher`** 并发研究并成文 → 拼装；
  - `DeepResearch`（`deep_research/main.py`）：走 `report_type="deep"`。
- `backend/server/websocket_manager.py:116 run_agent()`：按 `report_type` 分派 `multi_agents / detailed_report / 其它`。

## 5. 多 Agent 模式：`multi_agents/`（LangGraph）

- 图定义：`multi_agents/agents/orchestrator.py:65-105`，`StateGraph(ResearchState)`，8 个节点：
  `browser → planner → human → researcher → writer → fact_checker → visualizer → publisher → END`
- 两条**有界条件边**（这是原项目唯一"反思—回退"机制）：
  - `human`：`accept → researcher`，`revise → planner`（上限 `max_plan_revisions`）；
  - `fact_checker`：`accept → visualizer`，`revise → writer`（上限 `max_fact_check_revisions`）。
- 状态 Schema：`multi_agents/memory/research.py:5 class ResearchState(TypedDict)`，字段包括 `task / initial_research / sections / research_data / human_feedback / plan_revision_count / title / headers / table_of_contents / introduction / conclusion / sources / report / fact_check_notes / diagrams / fact_check_revision_count`。
- 执行：`orchestrator.py:149 run_research_task()` → `compile()` → `ainvoke({"task": ...}, config={"thread_id": task_id})`，带 LangGraph checkpoint 能力。
- **重要边界**：多 Agent 模式与标准模式**共享底层 `GPTResearcher`**，但两者的"状态、循环、评估"互不相通；多 Agent 的 `fact_checker` 是一次性 LLM 复核，没有量化指标。

## 6. 状态管理现状（标准模式）

标准模式**没有显式 State 对象**。所有跨步骤数据都是 `GPTResearcher` 的实例属性：

| 数据 | 位置 | 创建 | 更新 | 读取 |
| --- | --- | --- | --- | --- |
| 用户问题 | `self.query` | `__init__` | 不变 | 全流程 |
| 研究上下文 | `self.context` | `__init__=[]` | `ResearchConductor.conduct_research()` 末尾赋值 | `write_report`、图片生成、日志 |
| 已访问 URL（去重键） | `self.visited_urls: set` | `__init__` | `_get_new_urls()`、预取内容、DetailedReport 合并 | 引用生成、去重 |
| 已抓取来源 | `self.research_sources: list` | `__init__` | `add_research_sources()` | 报告/日志 |
| 成本 | `self.research_costs: float` + `self.step_costs: dict` | `__init__` | `add_costs()`（LLM 回调） | `get_costs()`、UI |
| 当前步骤 | `self._current_step: str` | `__init__` | 各阶段硬编码赋值 | `add_costs` 分桶 |
| 子查询计划 | **局部变量** `sub_queries` | `plan_research()` | 无 | 用完即弃 |
| 评估/反思结果 | **不存在** | — | — | — |

**结论**：
1. 状态是"过程式副产品"，没有版本、没有审计、没有把"计划"当一等公民；
2. 只有 `visited_urls` 被当作跨轮次资产（deep research 会把它递归传下去），其余都是"算完就覆盖"；
3. 多 Agent 模式有 `ResearchState`，但它只服务 LangGraph，无法被标准模式复用。

## 7. LLM 调用与成本机制

- 收口：`utils/llm.py:41 create_chat_completion()`。
- 计费：`utils/costs.py calculate_llm_cost()` → 若 provider 返回 `usage_metadata` 用它，否则 `tiktoken` 估算；结果以**美元**回调 `cost_callback`。
- 记账：`GPTResearcher.add_costs()` 累加 `research_costs` 并按 `_current_step` 分桶。
- **已有**：美元成本、按步骤拆分、日志事件 `cost_update`。
- **没有**：token 计数（只算钱不算 token）、调用次数上限、预算熔断、超时控制。这些是功能 D 要补的。

## 8. 报告生成与发布

1. `ReportGenerator.write_report()`（`skills/writer.py:49`）→ `generate_report()`（`actions/report_generation.py:209`）→ 单次 LLM 调用生成整篇 markdown；
2. 引用：`add_references(report, visited_urls)`（`actions/markdown_processing.py:104`）把 `visited_urls` 追加成 References 章节——**只保证"URL 出现过"，不保证"引用支撑结论"**；
3. 落盘：`backend/server/server_utils.py generate_report_files()` 输出 md/pdf/docx，`outputs/*.json` 记录事件流与 context/costs；
4. CLI：`cli.py` 额外写入 frontmatter（`_build_frontmatter`）。

## 10. 架构特征总结（改造视角）

| 特征 | 现状 | 对改造的含义 |
| --- | --- | --- |
| 流程形态 | 单向流水线（plan → search → scrape → compress → write） | 想加"循环"必须引入外层编排，不能靠改内部函数 |
| 并发模型 | `asyncio.gather` 并发子查询 | 天然适配"并发补充研究"，但缺少并发上限与熔断 |
| 状态 | 实例属性散落 | 需要新增独立 State 对象并"旁挂"，避免侵入 |
| 规划 | 一次性生成 N 条子查询，不落地、不执行追踪 | 功能 A 要新增"计划即数据"的表示 |
| 评估 | `SourceCurator`（可选）+ 多 Agent 的 `fact_checker`（非量化） | 功能 B 需要新的量化评估器；`evals/quality_eval` 可复用 |
| 反思 | 仅多 Agent 的 fact_check/writer 回退 | 功能 C 需要新的"评估→决策→补充研究"闭环 |
| 成本 | 美元成本 + 步骤分桶 | 功能 D 需要 token/次数/时长预算与熔断 |
| 可观测 | `research_observer` + `CustomLogsHandler` | 过程记录可直接复用 |
| 扩展点 | `create_chat_completion`、`research_observer`、`Config`、`prompt_family`、retriever 插件 | 改造应尽量复用这些缝，而非重构 |

**一句话概括**：原项目是"高质量的一次性研究流水线 + 一套并行存在的多 Agent 工作流 + 一套离线评测工具"，**具备全部底层能力（搜索、抓取、压缩、写作、成本、事件），但缺少把"计划—评估—反思—预算"当作一等对象来驱动循环的编排层**。
