## 1. 估算方法与口径（先讲清楚，避免误读）

DSH 会话不向外暴露精确 token 计数，因此本项目的数字全部是**估算**，用两种口径并列：

| 口径 | 定义 | 用途 |
| --- | --- | --- |
| **A 增量口径** | 只统计"新进入上下文的内容"：新读的代码行、新写的文档、新产生的工具输出 | 衡量"工作量"，用于对照任务书的开发预算 |
| **B 计费口径** | 每次模型调用都重发历史上下文，累计计费 token | 衡量"实际花费"，用于成本核算 |

两者差 2~3 倍。任务书里"阶段 0~1：2万~4万"显然是 A 口径；而账单看的是 B 口径。**本文件以 A 口径做预算，B 口径单列。**

估算方法：中文约 `1 token / 1.2 字`，英文约 `1 token / 4 字符`，代码约 `1 token / 3.5 字符`；工具输出按实际字符数折算。误差约 ±25%。

### 与任务书预算的对比

| 阶段 | 任务书预算 | 实际（A） | 偏差 | 原因 |
| --- | --- | --- | --- | --- |
| 0~1 | 2~4 万 | 7.1 万（含排查） | **+3~5 万** | ① 代码审计必须读真实实现（`agent.py` 816 行、`researcher.py` 1148 行、`deep_research.py` 670 行…），不能只看 README；② 4 份文档要求"每个判断都有代码依据"，输出量必然大；③ 额外的权限排查 0.7 万属计划外 |

> **结论：任务书预算偏乐观，主要低估了"读真实代码 + 写可验收文档"的成本。** 建议按修正后的预算执行（见第 4 节），而不是压缩设计质量。

## 6. 真实 API 成本（与 Token 无关，但要控制）

基线实测：**一次原版研究 ≈ $0.0111**（DeepSeek + Tavily）。

| 用途 | 次数（估） | 成本（估） |
| --- | --- | --- |
| 开发期冒烟（每批次 2~3 次） | ~15 次 | $0.17 |
| T25 对照实验（3 查询 × 2 版 × 2 轮） | ~12 次 | $0.13 |
| 阈值校准（5~10 查询，原版） | ~10 次 | $0.11 |
| 调试返工（预留） | ~20 次 | $0.22 |
| **合计** | ~57 次 | **约 $0.63**（改造版会更贵，估 $1.5 以内） |

> 若改用 full 评估，单次成本约 +$0.005，可忽略。

## 8. 超支预警与处置

| 信号 | 阈值 | 动作 |
| --- | --- | --- |
| 单批次实际 > 预算 1.5 倍 | 例如批次三 > 4.3 万 | 暂停，报告原因，由你决定继续/砍范围 |
| 单任务返工 ≥ 2 次 | — | 记录到 13 号风险清单，评估是否降级实现 |
| 总开发 > 18 万 | — | 砍 T13/T23（见第 3 节） |
| 真实 API 花费 > $3 | — | 暂停真实调用，改用 fake 测试 |
