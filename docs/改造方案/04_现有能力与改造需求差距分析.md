# 04 现有能力与改造需求差距分析

> 结论先行：原项目**具备全部底层能力**（搜索、抓取、压缩、写作、成本、事件），但**不具备把"计划—评估—反思—预算"当作一等对象来驱动循环的编排层**。
> 本文件逐项给出"已实现 / 部分实现 / 未实现 / 不建议改造"的判定与代码依据，并对每项改造标注**重复实现风险**。

---

## 1. 六项能力的判定总表

| 改造功能 | 对应原能力 | 判定 | 一句话结论 |
| --- | --- | --- | --- |
| 动态规划 | `plan_research_outline` → `generate_sub_queries` | **部分实现，需扩展** | 有"拆解"，无"计划对象/状态/修订"，本质是静态一次性拆解 |
| 状态管理 | `GPTResearcher` 实例属性；`ResearchState`(仅多 Agent) | **部分实现，需扩展** | 有数据，无结构、无版本、无持久化 |
| 质量评估 | `SourceCurator`、`fact_checker`、`evals/quality_eval` | **部分实现，需扩展** | 有"来源打分"和"二值事实复核"，**无量化质量评估** |
| 反思修正 | 多 Agent `fact_checker→writer` 回退；`deep_research` 追问下钻 | **部分实现，需扩展** | 有"回退"范式，无"依据评估结果决定补什么"的机制 |
| 循环控制 | `deep_research` 递归；LangGraph 条件边 | **部分实现，需扩展** | 标准模式无循环；deep 循环的停止条件与质量无关 |
| 成本控制 | `utils/costs.py` + `add_costs` | **部分实现，需扩展** | 有美元记账，**无 token/次数/时长预算与熔断** |

> 四项功能中**没有一项是"已经实现、可直接复用"**，但也**没有一项需要从零造底层**——这决定了改造的性质是"新增编排层"，而不是"重写"。

## 2. 逐项差距与证据

### 2.1 功能 A：Adaptive Planning（自适应研究规划）

**原项目有什么（证据）**

- 子问题拆解：`actions/query_processing.py:83 generate_sub_queries()` —— 1 次 LLM 调用，输出 `list[str]`（`_normalize_sub_queries` 兜底）。
- 计划载体：`skills/researcher.py:390` 的局部变量 `sub_queries`，用完即弃。
- 递归下钻：`skills/deep_research.py:396 deep_research()` —— 从结果抽 `researchGoal/followUpQuestions` 构造下一轮。
- 去重：`visited_urls`（`researcher.py:845`）。

**缺什么**

| 需求 | 现状 | 差距 |
| --- | --- | --- |
| 为每个子任务设定研究目标 | 子查询只有字符串，无目标/验收标准 | 需要 `SubTask{id, query, goal, status}` |
| 记录子任务执行状态 | 无 | 需要状态机（pending/running/done/failed/skipped） |
| 根据结果识别未解决问题 | deep 模式有 "followUpQuestions"，但只用于下钻，不回流规划 | 需要"信息缺口 → 新子任务"的显式映射 |
| 动态增删改子任务 | 无（计划不可变） | 需要计划版本 + diff |
| 避免重复研究已完成内容 | 只有 URL 级去重 | 需要"子任务级"语义去重（query 相似度 + 结论覆盖率） |

**重复实现风险（高）**：`deep_research` 的"追问下钻"已经是一半的动态规划。若新 Planner 另起炉灶、不复用其 `followUpQuestions` 抽取逻辑与 `visited_urls`，就会出现两套并行的"自我追问"机制，既浪费 token 又互相打架。

**建议**：新 Planner 复用 deep 的"结果→追问"抽取（可抽成公共函数），但把"追问"升级为"带 ID/目标/状态的任务"，并把计划**显式化、可版本化**。

### 2.2 功能 B：Research Evaluation（研究质量评估）

**原项目有什么（证据）**

- `skills/curator.py:38 curate_sources()`：1 次 LLM 调用给来源打分筛选，**只评来源可信度/相关性**，默认关闭（`CURATE_SOURCES=False`）。
- `multi_agents/agents/fact_checker.py:10 check_facts()`：一次 LLM 复核草稿，输出"问题清单或 None"，**二值 accept/revise，无分数、无指标**。
- `evals/quality_eval/metrics.py`：**离线**评估指标，已实现 `citation_faithfulness()`（引用忠实度）、`source_diversity()`（来源多样性）、领域质量打分等；`evals/hallucination_eval/`、`evals/simple_evals/` 另有两条评测线。
- `actions/markdown_processing.py:104 add_references()`：References 只是 `visited_urls` 的罗列。

**缺什么**

| 评估维度 | 现状 | 差距 |
| --- | --- | --- |
| 问题覆盖度 | 无 | 需要"计划子任务 ↔ 报告章节"映射 + 覆盖判定 |
| 关键结论证据支持率 | 无 | 需要把报告拆成"结论句"并逐条找证据片段 |
| 引用与结论匹配率 | 只有 URL 存在性 | 需要"引用 ↔ 结论"语义匹配（可用 `context/compression` 的相似度能力） |
| 引用链接有效性 | 无 | 需要 HTTP 检查（抓取器可复用，但要控成本） |
| 来源时效性 | 无 | 需要发布日期抽取（抓取内容里不一定有，误差大） |
| 来源冲突识别 | 无 | 需要跨来源比对，成本高，建议抽样 |
| 完整性 | 无 | 需要对照计划判定"应覆盖 vs 已覆盖" |

**重复实现风险（中）**：`evals/quality_eval/metrics.py` 已经有 `citation_faithfulness` 和 `source_diversity` 的实现。若新评估器完全另写，等于把已验证的指标逻辑重写一遍，且两套口径会不一致（对照实验时无法解释差异）。

**建议**：**在线评估器直接复用 `evals/quality_eval/metrics.py` 的纯函数**（零成本指标优先），只把"需要 LLM 判定"的部分新增为在线指标；不要重复实现文本解析与 URL 提取。

### 2.3 功能 C：Reflection & Revision（反思与修正）

**原项目有什么（证据）**

- 多 Agent：`multi_agents/agents/orchestrator.py:94-105` 两条条件边 `human→planner`、`fact_checker→writer`，**有上限**（`max_plan_revisions`、`max_fact_check_revisions` 超限强制 accept）。
- `deep_research`：结果 → 追问 → 递归下一层。
- 无任何"根据评估分数决定补研"的逻辑。

**缺什么**

| 需求 | 现状 | 差距 |
| --- | --- | --- |
| 由评估结果判断不足 | 无（评估本身就没有） | 需要 `EvaluationResult → Deficit[]` |
| 自动生成补充研究任务 | 无 | 需要 Planner 的"补研"入口 |
| 重新执行搜索与分析 | 有底层能力（`_get_context_by_web_search`） | 需要"只补缺口"的调用方式 |
| 根据新证据更新结果 | 无（报告一次成型） | 需要"定向修订"而非整篇重写 |
| 避免无意义重复搜索 | `visited_urls` | 需要"补研任务级"去重 |
| 保留每轮记录 | 只有扁平 JSON 日志 | 需要 `rounds[]` 版本化记录 |

**重复实现风险（高）**：如果 Reflection 再实现一套"判断是否继续"，会与 deep 的递归停止、多 Agent 的 revision 上限形成三套终止逻辑。**必须统一到 Budget/Termination 一处裁决。**

---

### 2.4 功能 D：Budget & Termination Control（预算与终止控制）

**原项目有什么（证据）**

- `utils/costs.py calculate_llm_cost()`：按 token 估算**美元**，优先用 provider `usage_metadata`。
- `agent.py:795 add_costs()`：累计 `research_costs`，并按 `_current_step` 分桶到 `step_costs`。
- 重试：`utils/llm.py:120` 非流式最多 10 次。
- deep：`depth/breadth` 粗粒度预算；multi_agents：revision 上限。

**缺什么**

| 需求 | 现状 | 差距 |
| --- | --- | --- |
| 最大研究轮次 | deep 有 depth，标准模式无 | 需要 `max_rounds` |
| 最大模型调用次数 | 无 | 需在 `create_chat_completion` 计数 |
| Token 预算 | 只算钱，不算 token | 需累计 `input/output tokens`（usage_metadata 已有） |
| 时间上限 | 无（只有单次 LLM 重试退避） | 需要 `deadline` + 每步检查 |
| 质量达标条件 | 无 | 需要 `EvaluationResult` 阈值 |
| 达到预算但质量不达标 | 无此概念 | 需要"明确报告未解决问题"的输出契约 |
| 禁止伪造完成 | **当前会**（研究失败仍写报告，见 02 号文档第 8 节） | 需要 `status: completed/partial/failed` + 缺口清单 |

**重复实现风险（中）**：美元成本已有一套记账。若预算模块另记一套，会出现"两套账对不上"。**建议：预算模块只做"限额判断 + 统一计数来源"，美元成本继续交由 `add_costs` 记账。**

## 4. 回答任务书提出的 7 个问题

### Q1：GPT Researcher 当前真实的 Agent 架构是什么？

**答**：**不是**单一 Agent 框架，而是"一个中心对象 + 三条并行产品线"：

- 中心：`GPTResearcher`（`agent.py`）持有 6 个 skill 与全部状态，对外只有 `conduct_research()` / `write_report()` 两个动作；
- 标准线：`ResearchConductor` 的 **async 流水线**（plan → 并发 search/scrape → compress → write），无循环、无评估；
- 深度线：`DeepResearchSkill` 的**递归下钻**（breadth×depth，带 followUpQuestions）；
- 多 Agent 线：`multi_agents/` 的 **LangGraph 状态图**（8 节点，2 条有界回退边）。

三者**共享底层能力，但状态与终止逻辑互不相通**。

### Q2：原项目已经有哪些规划、审核、反思和循环执行能力？

| 能力 | 已有的部分 | 边界 |
| --- | --- | --- |
| 规划 | 一次性子查询生成；deep 的追问下钻 | 计划不可见、不可修订、无状态 |
| 审核 | `SourceCurator`（来源打分，可选）；`fact_checker`（二值事实复核，仅多 Agent） | 不针对"结论—证据"，无量化指标 |
| 反思 | 多 Agent 的 writer 回退（有界）；deep 的追问递归 | 不是"由评估驱动的修正" |
| 循环 | deep 递归；LangGraph 条件边 | 标准模式没有循环；循环停止与质量无关 |

### Q3：原项目的哪些模块可以直接复用？

见 03 号文档。要点：**检索器、抓取器、LLM provider、上下文压缩、Markdown 处理、成本估算、事件钩子、报告落盘全部可直接复用**；`evals/quality_eval/metrics.py` 的指标函数可**直接改造为在线评估器**（这是最容易被忽视的复用点）。

### Q4：要实现 Adaptive & Reliable Research Agent，究竟需要新增和修改哪些模块？

- **新增 6~7 个**：`state / planner / evaluator / reflection / budget / orchestrator`（+ 可选 reporting）。
- **小改 6 处**：`utils/llm.py`（计数钩子）、`agent.py`（入口参数）、`skills/researcher.py`（失败语义 + 结构化证据）、`skills/deep_research.py`（预算接入）、`skills/writer.py`（定向修订）、`config/variables/*`（配置项）、`prompts.py`（新提示词）。
- **不改**：检索/抓取/向量库/MCP/多 Agent/离线评测。

### Q5：哪些改造可能与原项目现有功能重复？

见第 3 节 R1~R8。**最危险的三项**：R1（追问机制）、R4（引用忠实度指标）、R6（终止裁决）。

### Q6：当前技术架构是否适合实现动态研究和质量评估？

**适合，但有三个前提**：

1. **不需要 LangGraph 重写**。标准流程是线性 async，加"外层 while + 状态对象"即可；重写图会引入数周级回归风险（181 个既有测试依赖现有调用路径）。
2. **必须补一个"结论—证据"结构化中间层**。现在 `context` 是拼好的字符串，评估"每条结论是否有证据"无从下手；这是评估功能的**硬前提**。
3. **必须把 LLM 调用统一计数**。现在只有美元成本，没有 token/次数，预算控制无法落地；`create_chat_completion` 是唯一可行的挂载点。

### Q7：最合理、改造量最小且能真正落地的技术方案是什么？（**初步建议，阶段 2 再定稿**）

```
新增一层薄编排（不改原 conduct_research / write_report 的默认行为）：

  AdaptiveResearchOrchestrator
    state = ResearchState(query, plan=[], rounds=[], budget=..., evidence=[])
    while not budget.exhausted:
        state += round
        1) Planner.plan(state)          # 首轮拆解；后续按 gap 增删改
        2) for task in state.open_tasks: # 复用 ResearchConductor 的检索/抓取/压缩
              evidence += execute(task)  # 产出 {task_id, snippets[{url,title,text}]}
        3) report_draft = Writer.write(evidence, plan)     # 复用 writer
        4) evaluation = Evaluator.evaluate(report_draft, plan, evidence)  # 量化指标
        5) decision = Reflection.decide(evaluation, budget)  # supplement / replan / rewrite / finish
        6) if decision == finish: break
    final = Report with [评估结果附录 + 未解决问题]（若 partial/failed 必须写明）
```

**为什么这是最小方案**

- 底层 0 改动（除了计数钩子与失败语义）；
- 复用 deep 的"追问"思想与 `evals` 的指标实现；
- 终止裁决集中在 `Budget`，天然满足"不无限循环"；
- 原版 `GPTResearcher` 保持可独立运行 → **天然满足"保留原版对照"**（同一份代码，两种入口）。

**改造量对比**

| 方案 | 改造量 | 风险 | 评价 |
| --- | --- | --- | --- |
| 在 `ResearchConductor` 内部加循环 | 小 | **高**（污染热点路径，181 个测试受影响） | ❌ 不建议 |
| 新编排层 + 旁挂状态（本建议） | 中 | 低（默认路径不变） | ✅ 推荐 |
| 用 LangGraph 重写标准流程 | 大 | 高（数周 + 回归风险） | ❌ 不建议 |
| 复用 `deep_agents`（deepagents 包） | 中 | 中（依赖未装、范式不同） | ❌ 不建议 |

## 6. 风险判断

| 风险 | 等级 | 说明 | 缓解 |
| --- | --- | --- | --- |
| 评估成本失控 | **高** | 每轮多项指标都调 LLM，token 可能翻 3~5 倍 | 零成本指标优先；LLM 判定只用于"引用匹配"；抽样 |
| 同模型自评偏差 | **高** | 三档模型同为 deepseek-chat，评估者与被评估者是同一模型 | 引入规则校验（URL 是否存在于证据集）作为交叉验证 |
| 改动热点路径引发回归 | 中 | `skills/researcher.py` 是主路径 | 失败语义改造放最后一批，配回归测试 |
| 重复实现（R1/R4/R6） | 中 | 造成两套口径、双倍成本 | 复用清单 + Code Review 检查点 |
| 环境不可测 | 中 | pytest 未安装、`RETRIEVER` 无效、embedding 未配置 | 开发前先修环境（需授权） |
| 无基线标签 | 中 | 无法严格对照 | 阶段 3 先打 tag |
| 过度设计 | 低 | 加 DB / 加框架 | 明确不引入新依赖 |
