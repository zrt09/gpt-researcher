## 1. 快速开始

### 1.1 环境

```powershell
# 依赖已装在仓库内的 env/ 虚拟环境
env\Scripts\python.exe --version          # Python 3.13.2
env\Scripts\python.exe -m pytest tests\ -q # 全量测试
```

### 1.2 跑原版（不变）

```powershell
env\Scripts\python.exe cli.py --report_type research_report "你的研究问题"
```

### 1.3 跑自适应版

```powershell
env\Scripts\python.exe cli.py --adaptive --adaptive_rounds 3 "你的研究问题"
```

- `--adaptive`：走"规划 → 研究 → 评估 → 反思 → 补研"循环
- `--adaptive_rounds`：本次运行的轮次上限（默认取 `ADAPTIVE_MAX_ROUNDS`）
- 不需要 `--report_type`（自适应模式固定产出 research_report 风格）

### 1.4 产物

```
outputs/
├── <报告标题>.md / .docx            # 最终报告（含"研究质量自检"附录）
└── adaptive/<run_id>/
    ├── state.json                   # 全量状态：计划/证据/结论/每轮指标/预算
    ├── report_v1.md, report_v2.md   # 每轮草稿（可对比修改过程）
    └── final_report.md              # 最终报告（含附录）
```

## 2. 配置项（`.env` 或配置文件）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `ADAPTIVE_ENABLED` | `false` | 预留开关；CLI 用 `--adaptive` 时不受它限制 |
| `ADAPTIVE_MAX_ROUNDS` | `3` | 最大轮次 |
| `ADAPTIVE_MAX_LLM_CALLS` | `120` | 模型调用上限 |

| `ADAPTIVE_MAX_SECONDS` | `900` | 墙钟上限 |

| `ADAPTIVE_MAX_TASKS` | `8` | 计划任务总数上限（含补研任务） |
| `ADAPTIVE_MAX_TASKS_PER_ROUND` | `4` | 单轮执行任务数 |
| `ADAPTIVE_CONCURRENCY` | `3` | 单轮并发 |

## 3. 三种终态的含义

| 状态 | 含义 | 报告里有什么 |
| --- | --- | --- |
| `completed` | 分项指标全部过门槛，`stop_reason=quality_met` | 质量自检表格（通过项） |
| `partial` | 预算/无进展/结构问题导致停止，质量未达标 | 5 段式附录：停止原因与资源、未达标指标、未解决任务、已知薄弱点、建议 |
| `failed` | 规划失败、报告无法生成等硬失败 | 失败原因 + 已完成部分 |

**代码层面强制**：`completed` 必须同时满足 `stop_reason=quality_met` 且 `evaluation.passed`，否则 `ResearchState.validate()` 抛错。

## 4. 已知问题

### K-1 两个既有测试长期失败（**非本次引入**）

`tests/test_logging_output.py::test_log_output_file`、`tests/test_researcher_logging.py::test_researcher_logging`。
已在 `main` 分支复跑确认同样失败；前者是文件名 glob 结构不匹配，后者依赖真实网络（Tavily 401/连接重置）。按"不许改测试让测试通过"的约束，未处理。

### K-2 `light` 模式的覆盖度偏保守

任务归属依赖"章节标题/结论句 ↔ 任务目标"的词面相似度，外加"引用 URL 属于该任务证据"。同一查询的三次运行覆盖度从 0.625 到 1.0 波动，主要来自 LLM 报告的主题组织方式差异。
**影响**：可能多做一轮补研（成本略增），不会漏报成功。
**缓解**：`full` 模式由 LLM 直接标注任务归属，更准但更贵。

### K-3 模型调用/token 计数可能偏低

实测一次 2 轮运行记录 8 次调用，但日志显示至少 8 次子任务规划 + 2 次写作 + 1 次总规划 ≈ 11 次。
**影响**：预算是硬约束，但计数不是精确账单；`ADAPTIVE_MAX_LLM_CALLS` 可能比预期更晚触发。
**待查**：并发子任务下的用量上报路径（`contextvars` + 执行器包装）需要一次专门的埋点核对。

### K-4 成本估算偏高（价目表不匹配）

`utils/costs.py` 内置 OpenAI 价目表；DeepSeek 等模型走默认 $5/M 输入、$15/M 输出，实际便宜约 10~20 倍。
**影响**：`max_cost_usd` 会比预期更早触发；对照实验里的 $0.0627 是上界。

### K-5 来源时效性指标恒为 `None`

证据里没有 `published_at`（抓取器未回填），该指标只作展示、不参与门槛。要启用需在抓取阶段解析发布日期。

### K-6 写作失败时降级为"证据摘要"

写作模型连续失败时，系统会生成不带撰写的证据摘要，并强制把状态降为 `partial`、在未解决问题里写明"写作模型不可用"。
**这是有意的**：宁可在报告里承认退化，也不返回空报告或假装完成。

### K-7 Web 后端未接入自适应入口（原计划 T23，**主动延后**）

`backend/server/*` 仍只走原版路径；`/report`、`/ws` 没有 `adaptive` 参数。
**原因**：Token 预算逼近上限（39 万），而 T23 属于"入口扩展"，不影响"可运行的改造版"验收；同时它需要改动 WebSocket 日志格式，回归风险高于收益。
**后续**：在 `websocket_manager.run_agent` 里加一个 `report_type == "adaptive"` 分支即可，预计 4k token。

### K-8 前端不展示评估结果

评估指标只写在报告附录里；前端仍是原版 UI。

### K-9 报告语言不受配置控制

`LANGUAGE=english` 不生效，模型按上下文自行选择语言（英文查询曾产出中文报告）。对照实验因此只比较结构指标。

## 5. 后续改进建议（按性价比排序）

| # | 建议 | 收益 | 成本 |
| --- | --- | --- | --- |
| 1 | 修 K-3（用量计数埋点） | 预算真正可控 | 低 |
| 2 | 让 `full` 模式成为可选默认 | 质量评估更接近"结论级" | 中（成本上升） |
| 3 | writer 只重写受影响章节 | 降本 30~50% | 中 |
| 4 | 抓取阶段回填 `published_at` | 时效性指标可用 | 低 |
| 5 | 接 K-7 后端入口 + 前端展示评估 | 可用性 | 中 |
| 6 | 清理 `competitor_monitor` / `competitive_intel` 残留目录 | 消除无效检索器 | 极低（需授权删除） |
